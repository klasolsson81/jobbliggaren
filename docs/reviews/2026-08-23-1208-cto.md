## Axis 1 — the decision

### Why the sink is the wrong object

Condition 2 is written as a property of **what the sink holds**. Every remedy aimed at
the sink's contents is therefore an *observation*, and the session's own measurement A
is exactly that: a corpus reading, true on 2026-08-23 by luck rather than by
construction. A corpus measurement is not a write-path measurement — 548 address-shaped
strings with zero consumer-mail domains says nothing about the next registration.

`LogEmail` is the **sole producer** of that material (measurement E: all eight
`IEmailSender` methods funnel through one private `[LoggerMessage(3001)]`). A single
choke point means the write path is a *complete cut* of the producer set, so an
invariant enforced there holds for every future write — strictly stronger than any
reading of the sink, which only ever covers writes already taken.

This is the repo's own rule, not an import. AGENTS.md §2.2: *"Aggregates protect
invariants in constructors/methods, not handlers"* — invariants are enforced where the
state is produced (Evans 2003, "Aggregates"). Condition 2 stops being something anyone
re-measures and becomes something the writer cannot violate.

The instrument is a fitness function in the strict sense (Ford/Parsons/Kua 2017, ch. 2):
an architectural characteristic given an objective measure that runs continuously. The
unit test is Klas's **"fäller"** — every CI run. The `Warning` line is his **"larmar"**.
Neither is a sentence.

### The shape — four corrections to the sketch as presented

The session's Variant D sketch is right in principle and wrong in four details. Each
correction has a repo-native ground; none is taste.

**(a) The allow-list is a pure RFC suffix rule with zero bespoke entries.**
Not "…plus `e2e.jobbliggaren.test`". That address is already covered by the `.test`
TLD. Measured — every recipient that legitimately reaches `ConsoleEmailSender` is
already under a reserved suffix:

| Address in repo | Covered by |
|---|---|
| `user@example.com` (the `ConsoleAndNull*` unit tests) | RFC 2606 second-level |
| `klas@jobbliggaren.test` (`AdminBootstrapOptions.cs:18`, the documented dev login) | RFC 6761 `.test` |
| `test-e2e-*@e2e.jobbliggaren.test` (`tests/e2e/helpers/auth.ts:18`) | RFC 6761 `.test` |
| `*@bemanning.example`, `*@drift.example` (`RecruiterContactIngestTests`) | RFC 6761 `.example` |

So the rule is: RFC 6761 TLDs `.test` · `.example` · `.invalid` · `.localhost`, plus
RFC 2606's `example.com` · `example.net` · `example.org`. **Nothing else, ever.** A
list with named exceptions invites growth and has no external arbiter; a suffix rule
whose authority is an RFC cannot drift, and a reviewer can check it against a
document neither we nor Klas control (OCP — Martin 2017, ch. 8: extend by adding
recipients under the rule, never by editing the rule).

**(b) The suppressed line is kind-only. No address — not even masked.**
This is not my preference; it is a binding precedent in the same file family that
names this issue by number. `NullEmailSender`'s XML doc:

> *"**The payload stays kind-only.** Warning reaches a durable sink, so a recipient or
> token added here later 'for debuggability' becomes durable PII (CLAUDE.md §11,
> #1208). The level is the change; the shape is the invariant."*

A masked address is still a partial identifier and re-opens the door that sentence
closes. The developer does not need it — they know the address they typed. The two
senders' declined-send lines are **one knowledge piece** ("what a sender may say when
it declines to write recipient material"), so they take one shape (Hunt/Thomas 1999,
DRY as knowledge). **Shape parity, not extraction:** do not hoist a shared base class
for two eight-method senders — that is speculative generality. The single home for the
invariant is the *test*, which asserts it of both senders.

**(c) The allow-list is a constant in the Console arm. Never `EmailOptions`.**
Two grounds, and the first is already settled in that file. `EmailOptions`' own doc
records why provider-specific config was moved out (#220, a dead `AwsRegion`): *"den
här klassen konstrueras av VARJE avsändare … så en providers credentials på den hade
gjort en provider-detalj nåbar från armar som inte har någon (ISP)."* An allow-list is
a Console-arm detail; putting it there repeats the exact violation #220 repaired
(ISP — Martin 2017, ch. 10). Second, and decisive: **a configurable allow-list fails
open.** Anything settable to `*` is a hole with a config key in front of it. A
compile-time constant cannot be widened at runtime, which is the whole property being
bought.

**(d) `CanDeliver` stays `true`, and the gate never reads it.**
Named because the mistake is available and expensive. `AuthOptionsValidator` refuses to
boot on `CanDeliver == false`, and `ChangeEmailCommandHandler` /
`RequestPasswordResetCommandHandler` return 503 on it. An implementer reasoning "the
body can't be shown, so we can't deliver" would strand every dev registration and trip
a boot guard. The gate changes **what is written to the log**, never the delivery
contract.

### The instrument, and what it must pin

Three assertions, home `tests/Jobbliggaren.Application.UnitTests/Email/` beside
`NullEmailSenderSuppressionLogTests` (the established seam for pinning a sender's log
shape):

1. **The property.** Reserved recipient → `Information`, body present. Non-reserved
   recipient → `Warning`, kind only, **and the body string absent from the emitted
   line**. Assert on absence of the body, not on presence of the warning: a guard that
   only checks the new line passes while the old one still fires.
2. **Growth of the surface.** The case count must equal
   `typeof(IEmailSender).GetMethods()` arity (less the `CanDeliver` getter). A ninth
   method added outside the gate then fails a test instead of passing silently. A guard
   that closes today's members does not close tomorrow's.
3. **Growth of the allow-list.** Pin the membership set exactly. Adding `gmail.com`
   must fail a named test, not merely look wrong in review.

### The §11 rewording

Delete the prose condition; do not correct it. Replace it with §11's own house form —
the mechanism plus the test that pins it, exactly as the neighbouring paragraph reads
(*"`UseHttpsRedirectionGateTests` pins both middleware gates in both polarities"*).

The new sentence must claim **only what the gate delivers**: the *email-body path*
cannot write a non-reserved recipient's body. It must **not** claim the sink holds no
real-user PII of any kind — the gate does not reach other log lines, and that residual
is unmeasured. State the residual in the same sentence. §11 already uses that form
verbatim (*"What the guard does NOT cover, stated so the scope is not read wider than
it is"*), and §9.6 requires it: a fix deletes text or changes code, it never adds a
claim-sentence. Narrowing a claim to the truth needs no one's grant.

## Rejected alternatives

### Variant A — a retention policy on the dev Seq. Rejected.

Foreclosed by the commit at HEAD. `75dbba78` (#1170) measured, on the **production**
box, that Seq has no declarative retention surface and that no policy was ever set —
four agreeing instruments, 2384 of 2384 passes at `Count 0`. Its ruling was to *delete*
the promise, and its commit message states the ground: *"The claim this PR deletes was
prose, so nothing could have failed when it drifted."* Writing a dev-Seq retention
policy into §11 one commit later would recreate that defect class, in the same section,
against the same product.

On the merits it also fails on its own terms. Retention bounds **age, not content**: a
seven-day policy means condition 2 is *false for up to seven days* by design. It does
not fall or alarm when broken — it deletes the evidence that it was broken, which is
the opposite of what Klas asked for. And it is per-developer operator state living in a
container volume: no PR can deliver it, no CI job can read it, and no reviewer can
verify it (12factor.net III — config that is not in the environment and not in the repo
is unmanaged state).

Not composed with D either. Adding an unverifiable obligation beside a verifiable one
weakens the verifiable one by association.

### Variant B (pure) and B′ — stop logging the body. Rejected.

B destroys a delivered capability to close a case D closes at no cost. `CanDeliver`'s
XML doc marks the flow load-bearing and argues it substantively (#1087): the developer
completes a token→email→confirm flow by reading the link out of the log, so
delivery-dependent handlers behave in dev as they will in production. B trades that for
a property obtainable without touching it. Regel 2: a reviewer asked to choose between
"removed the feature" and "gated the feature on the recipient" does not pick the first.

B′ (log only the link) is not a mitigation and should be named as such rather than
weighed: the link **is** the token. It relocates the sensitive material without
reducing it.

Note what D preserves that B does not: under D the dev flow is **unchanged** for every
recipient that already appears in the repo (table above), because they are all already
reserved. B breaks the flow for all of them.

### Variant C — formal acceptance with expiry, §9.6 (3). Rejected.

Rejected first on Klas's own words. His stated end state is *"något som fäller eller
larmar när det bryts — **inte en mening**"*. A signed accepted-risk ADR with a lapse
trigger and a named human reader is, precisely and by construction, a mening.

Rejected second on what the route is for. §9.6 (3) grants an acceptance because
*"nothing detects a lapse automatically"* — it is the instrument for risks that
**cannot** be mechanised. Here a mechanism exists, is cheap, and is bounded to one
class. Accepting a mechanisable risk is the snabblösning wearing procedure, and Regel 4
requires naming it rather than weighing it politely.

Third, it would cost the session a block for nothing: C needs a Klas grant **and**
`security-auditor`'s signature, neither of which a subagent can solicit (§9.2 — no
subagent can prompt Klas). Choosing C converts a deliverable session into a waiting one.

I take **no position** on whether the §9.6 (3) bound would hold if it were reached. It
is not reached, and it is not mine to grant.

### Variant E — a repo-side script a developer runs. Rejected.

This is the issue's rejected fourth outcome with a shell script attached. Nothing
triggers it; an instrument with no trigger measures nothing, and "keep watching" does
not become a mechanism by being scripted. The session read this correctly.

## Trade-offs accepted

**A developer who registers with a real address in local dev loses the emailed link.**
That is the intended failure and its cost is near zero: the documented dev login is
already `klas@jobbliggaren.test` (`AdminBootstrapOptions.cs:18`) and the E2E helper
already mandates `.test` on RFC 6761 grounds. The remedy for a developer who hits the
warning is to use the address the runbook already tells them to use.

**No escape hatch, deliberately.** An opt-in flag re-introduces the hole with a key in
front of it and would be set once and forgotten. Declining it is the point of (c).

**A reserved-domain notion enters C# for the first time.** Accepted. It exists already
in TypeScript (`auth.ts`) and de facto in the C# fixtures; this makes it a rule with an
external authority instead of a convention held by memory.

**The gate covers the email-body path only.** Other PII paths into dev Seq remain
unmeasured. Accepted and *stated in §11* rather than filed — a documented scope
boundary in a tracked file every lane reads is disposal; it is not an unowned gap.
