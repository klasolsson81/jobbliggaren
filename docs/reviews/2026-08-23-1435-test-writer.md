### Major 2 — the one-channel-per-table argument (a row matching two arms is counted ONCE) is asserted nowhere

**Where:** the claim lives in `src/` twice — `ErasureCascadeRegistry.cs:249-254` (*"A single row
can match on organization_number AND on filter for the same identifier … so two channels would
count that row twice in `Matched.Total`, which drives the outcome word"*) and
`IRecruiterErasureMatchQuery.cs` on `CountCompanyWatchFollowsAsync`. The PR body promotes it to
the lead design decision. **No fact seeds such a row.**

Every one of the six `CompanyWatchFollows` facts matches on **one** arm. Nothing distinguishes
`SELECT count(*) … WHERE a OR b` from a shape that counts matches instead of rows.

Why it matters beyond tidiness: the number reaches a data subject in an Art. 17 reply. A
disclosure that says *two* company-watch surfaces when there is *one* row is a wrong statement
about what we hold, and the registry's own comment says this is the reason the two columns share a
channel at all. An argument carried only by a comment is one refactor from being lost.

The premise is §5-clean and needs no disclosure: a ten-digit token is a legal `WatchFilterSpec`
element under the shape-only grammar (`ConceptIdPattern` = `^[A-Za-z0-9_-]{1,32}`,
`WatchFilterSpec.cs`), which is precisely what the `company_watches:MatchedHumanErases` ground
already asserts in writing — *"Karlsson, Anna-Karlsson and a ten-digit org.nr all persist."* The
seed goes through `CompanyWatch.SetFilter` via the existing `SetWatchFilterAsync` helper. No new
helper needed.

```csharp
/// <summary>
/// ONE ROW, TWO ARMS, ONE COUNT. A ten-digit org.nr is a legal WatchFilterSpec element under the
/// shape-only grammar, so a watch ON an employer can also FILTER on that employer's number - and
/// then a single row satisfies both disjuncts for one identifier. This is the whole reason the two
/// columns share ONE channel instead of two: two channels would report this row twice in
/// Matched.Total, and Total is what the reply template's outcome word is derived from.
/// <b>Mutation:</b> split CountCompanyWatchFollowsAsync into two counts summed, or give the two
/// columns their own reported surfaces, and only this fact goes red.
/// </summary>
[Fact]
public async Task A_row_matching_BOTH_arms_is_counted_ONCE_and_not_twice()
{
    var ct = TestContext.Current.CancellationToken;
    var watchId = await SeedFollowThroughExecutorAsync("5566778899", ct);
    await SetWatchFilterAsync(watchId, "5566778899", ct);

    var probe = await EraseAsync("5566778899", ct, dryRun: true);

    probe.Matched.CompanyWatchFollows.ShouldBe(1,
        "count(*) over `a OR b` counts ROWS. Two channels, or two summed counts, make this 2 - "
        + "and the Art. 17 reply then tells her we hold two watches where we hold one.");
}
```

**The exact `src/` edit that turns it red** (green today):

```csharp
// src/Jobbliggaren.Infrastructure/JobAds/RecruiterErasureMatchQuery.cs
// CountCompanyWatchFollowsAsync - replace the single OR-ed count with two summed counts:
var byKey = await CountAsync($"""
    SELECT count(*)::int AS "Value" FROM company_watches
    WHERE organization_number = {storedKey} OR organization_number = {plain}
    """, cancellationToken);
var byFilter = await CountAsync($"""
    SELECT count(*)::int AS "Value" FROM company_watches
    WHERE lower(coalesce(filter::text, '')) LIKE {pattern} ESCAPE {LikeEscapeSql}
    """, cancellationToken);
return byKey + byFilter;   // <- 2. Nothing in the suite as merged notices.
```

Equivalently: split `CompanyWatchFollows` into two entries in
`ErasureCascadeRegistry.ReportedSurfaces` + `ErasureSurfaceCounts`. Every architecture fact
(`The_reported_surface_counts_match_the_registry`, `Total_sums_EVERY_reported_surface…`,
`Every_channel_names_a_real_port_method_and_a_reported_surface`) stays green through that split,
because each checks *correspondence*, never *cardinality per table*.

### Major 3 — `CompanyWatchFollows` has no negative control; the file's own convention has one for its sibling channel

**Where:** the convention is delivered for `JobSeekerProfiles`
(`Only_the_seeded_profile_is_counted_while_two_neutral_profiles_are_NOT`, `:1605`) and absent for
`CompanyWatchFollows`.

Every follows fact seeds **exactly one** `company_watches` row. Therefore:

```csharp
OR lower(coalesce(filter::text, '')) LIKE {pattern} ESCAPE {LikeEscapeSql}
// mutate {pattern} -> '%'
OR lower(coalesce(filter::text, '')) LIKE '%'
```

makes every watch row match unconditionally — and **all six follows facts stay green**, because
each seeds one row and each asserts `ShouldBe(1)`. The same is true of dropping the identifier
from `LikePattern` for this arm. The profiles channel catches the identical mutation on all three
of its disjuncts; the follows channel catches it on none.

This is the file's stated convention, not an invention of mine: *"a negative control written in
the POSITIVE form."* It exists once and is owed twice.

```csharp
/// <summary>
/// The count is the MATCHING watch and not the table. Written in the positive form: two watches
/// exist, exactly one carries the identifier. Without this, replacing the filter pattern with a
/// bare wildcard leaves every other follows fact green - each seeds a single row, so an
/// unconditional match and a correct match are the same number.
/// <b>Mutation:</b> replace the pattern with a bare wildcard on the filter disjunct.
/// </summary>
[Fact]
public async Task Only_the_matching_watch_is_counted_while_a_neutral_watch_is_NOT()
{
    var ct = TestContext.Current.CancellationToken;
    var hers = await SeedFollowThroughExecutorAsync("5566778899", ct);
    await SetWatchFilterAsync(hers, "Rosenlund-Vikander", ct);

    var other = await SeedFollowThroughExecutorAsync("5561234567", ct);
    await SetWatchFilterAsync(other, "Marianna-Ek", ct);

    var probe = await EraseAsync("Rosenlund-Vikander", ct, dryRun: true);

    probe.Matched.CompanyWatchFollows.ShouldBe(1,
        "a bare wildcard on the filter arm makes this 2 - and every single-row follows fact "
        + "cannot tell the two apart.");
}
```

Distinct user ids come free from `SeedFollowThroughExecutorAsync`'s `Guid.NewGuid()`, so the
partial unique index is not in play (see answer 6).

**The exact `src/` edit that turns it red:** in `CountCompanyWatchFollowsAsync`, replace
`LIKE {pattern}` with `LIKE '%'` on the filter disjunct, or change `LikePattern`'s return to
`"%%"` for this call site. Green today.

**Fallback if container cost is the constraint:** Major 2's and Major 3's facts can be merged into
one — seed the matching watch with the org.nr *in* its filter, plus one neutral watch, assert `1`.
Both mutations then redden it. I recommend keeping them separate, per the file's

## Major A (ny i deltat) — den nya negativa kontrollen kunde inte falla för sin egen mutation

`Only_the_seeded_follow_is_counted_while_two_neutral_follows_are_NOT` namngav mutationen *"bare
wildcard on any follow disjunct"* — och den mutationen förblev **grön**. De två neutrala raderna
saknade filter, och `jsonb_path_query` är **strict**, så NULL uteslöt dem innan mönstret ens
konsulterades. *"Före deltat gjorde den gamla coalesce-formen dem sanna, så kontrollen korsade
tröskeln då och gör det inte nu — deltats egen SQL-omskrivning tog bort just den diskrimineringen."*
**Åtgärdat:** båda neutrala rader har egna filter. **Mutation körd efteråt: 1 failed / 1.**

## Minor B (ny i deltat) — samma sak på profilsidan

**inget** faktum fångade längre en alltid-sann `match_preferences`-disjunkt. **Åtgärdat:** en neutral
profil bär icke-tomma preferenser. **Mutation körd efteråt: 1 failed / 1.**

## Minor C (ny i deltat) — pinnen saknade excludedness-länken

`company_watches` gjorde) passerar pinnen och slutar tyst korsa tröskeln. **Åtgärdat:**
