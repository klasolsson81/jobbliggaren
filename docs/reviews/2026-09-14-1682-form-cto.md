## D1 — job trigger

**Verdict: (a) — own config-driven cron, clock-padded after the snapshot window. Default `35 3 * * *` UTC, own options section, own `Enabled` kill-switch.**

**Binding reason.** (b) is fidelity to the *wrong writer*. `MAX(occurred_at) WHERE JobType = 'snapshot'` moves once a day; `job_ads` moves every ten minutes, because `SyncPlatsbankenStreamJob` writes it on `*/10` and stamps `JobType = "stream"`. The two saved probes are themselves the witness: the Seq Scan in `probe4.out` counts **83 308** in-window ads against the brief's **83 280** two minutes earlier. So (b) buys a level-trigger that fires exactly as often as a daily cron while *looking* like it tracks ingest — a mechanism whose stated property is false by construction, which is the `#805-3` vacuous-guarantee shape this repo names twice. Widening the watermark to *any* `JobAdsSynced` row inverts the defect: 144 rebuilds/day for a distribution that moves by fractions of a percent.

The quantity is a **distribution over 83k ads**, not a live count. Under Klas decision 2 (window = Active + Archived) an `Active→Archived` transition is a no-op, so only inserts and Art. 17 erasures move it. Cadence is therefore a cost question, not a correctness question — and cost is 163 ms (`probe4.out`, `Execution Time: 162.852 ms`, 62 358 shared-hit buffers, HashAggregate over a Memoize'd index scan). KISS/YAGNI decide it.

`35 3 * * *`: the only hard dependency is the snapshot's window (`Cron.Daily(2)` + `DisableConcurrentExecution(3600)` → clear at 03:00), and 03:35 sits in the existing ingest-consumer cluster (retain 03:15, matching 03:20, watch-scan 03:25, expire 03:45) with 10 minutes' padding either side. Config-driven per the two nearest precedents (`ScbRegister:SyncCadenceCron`, `CompanyWatchMaterialisation:CadenceCron`).

**Own options section, not `CompanyWatchMaterialisation:`.** Different change-reason (SRP, Martin 2017 ch. 7): that job resolves user predicates against the register; this one aggregates `job_ads`. And it must not hang off another feature's `Enabled` — that is verbatim `security-auditor` Major 3 (ADR 0139), whose measured point is that a cadence tied to a flag defaulting `false` never runs at all.

**Rules out.** (b) — false fidelity, one audit read per tick, a second reason to run, for nothing. (c) — ADR 0139 clause (ii) settled the doctrine (*"the committed state IS the queue"*), and `SyncPlatsbankenSnapshotJob` is Application while Hangfire is Worker.

**Conditions.** Kill-switch `Enabled` (default `true`), degrading honestly to *no block rendered* — never a zero (ADR 0120). A staleness bound **derived, not chosen**: refuse to render when the profile is older than **two cadence intervals** (48 h on a daily cron) — one missed run is transient, two consecutive is a broken job. And: **the issue's own acceptance wording *"runs once per completed ingest run"* is unsatisfiable as written** and must be reworded in the PR that closes it, or it will be graded false.

## D2 — the match surface

**Verdict: M2, but the framing is wrong — this is REUSE of `IOccupationCodeDeriver`, not a new crosswalk read.**

**Binding reason.** CLAUDE.md §9.1: *check existing patterns (reuse, don't invent)*. The delivered engine already answers exactly D2's question — free-text word → ranked ssyk-4 occupation groups, via occupation-**name** labels resolved up through the frozen map, two passes (exact `OrdinalIgnoreCase`, then Snowball stemmed-overlap gated on `MaxGroupSpread = 4`), singleton-cached with no per-call DB hit, `Title`/`MatchKind`/`MatchedOn` carried as cited evidence. Its own measured docblock names **both** worked words as focused/signal tokens (`systemutveckl` spread 1, `sjuksköterska` spread 2). The port is `Application`, the implementation `Infrastructure`, and a CQRS adapter (`DeriveOccupationCodesQuery`) already exists.

M2-as-described would build a *second* answer to *"what occupation does this word denote"* — DRY in its real sense (Hunt/Thomas 1999: one home per knowledge piece), and the `#1407/#1471` divergence class ADR 0139 exists to close.

**Rules out.** **M1** — a new token-aware matcher beside a delivered one, and it fails the issue's own acceptance by the brief's measurement (`sjuksköterska` matches while typing, then vanishes on the last letter). Note also that today's `TaxonomyReadModel.SuggestByPrefixAsync` is a plain `Label.StartsWith(prefix)`, so M1 is *not* reuse of that either — it is a third mechanism. **M3** — `tools/sni-aliases/README.md` is explicit: `SearchSynonyms:Occupations` *"is a different axis in a different bounded context, and neither map is a mapping of the other"* (Evans 2003, bounded contexts), and the brief concedes it adds nothing M2 finds.

**Condition — measure before writing copy.** The probes measured `ILIKE %word%` over labels. The deriver is a **different operator** (exact + stemmed, spread-gated). Call `DeriveAsync("systemutvecklare")` and `DeriveAsync("sjuksköterska")` against the live snapshot **on day one**: the docblock's spread figures suggest `sjuksköterska` may resolve to ~2 groups, not the brief's ~10, and if `systemutvecklare` returns empty the first acceptance criterion fails outright. ## D2b — when a word resolves to several groups

**Verdict: none of (i)–(iv). Rank and confirm: name the resolved groups as a ranked choice, the user picks ONE, that group's distribution renders. One group resolved ⇒ skip the chooser, render directly, naming the group.**

**Binding reason — this is forced, not preferred.** AGENTS.md §5 lists *"SSYK derivation without user confirmation (taxonomy lookup + confirm, ADR 0040)"* as an anti-pattern, and §12 makes a §5 anti-pattern merge-blocking. `IOccupationCodeDeriver`'s contract states the invariant: *"The engine PROPOSES a ranked candidate list; the user CONFIRMS — it never auto-selects"* (ADR 0040 Beslut 4, *"the load-bearing transparency invariant"*).

**Rules out.** **(ii)** largest group only and **(iii)** top-K are auto-selection with an invisible cutoff. **(iv)** is the worst and is falsifiable from `probe2.out`: `Grundutbildade sjuksköterskor` carries 3 317 ads against roughly 550 across the nine specialist groups, so a union-weighted "distribution over matching occupations" is **~86 % one group wearing a plural label** — an opaque aggregate over an unconfirmed derivation, breaking §5 twice. **(i)** is the wall the issue exists to remove.

**Why the chooser is not a second wall.** The issue's complaint is *"a wall of codes"*. This renders group **names** (`Grundutbildade sjuksköterskor`, `Anestesisjuksköterskor`), each an actionable choice, capped at the deriver's `MaxCandidates = 25`. Codes were the wall; choices are not.

**For Klas:** this adds one visible step you have not seen — typing a word may ask which occupation you meant before showing the map. It is forced by §5 + ADR 0040, so it is not mine to trade away, but the UX consequence is yours to react to.

## D4 — floor

**Verdict: N ≥ 21. Derived, and it moves if the threshold moves.**

**Binding reason.** The issue's own threshold is ≥ 5 % per division. A single ad clears it whenever `100/N ≥ 5`, i.e. `N ≤ 20`; at `N = 21`, `100/21 = 4.76 %` does not. Below 21 the "≥ 5 % list" is therefore an enumeration of individual employers wearing the grammar of a distribution — the surface would be claiming a shape the data cannot carry. 21 is the smallest N at which one ad cannot clear the threshold alone, and it is a *function of the threshold*, not a number someone liked.

**Measured effect** (`probe4.out`): 310 of 395 groups render, **85 refused**, 1 132 rows kept.

**Rules out.** "Two ads cannot clear" → `200/N < 5` → **N ≥ 41**, not 40 (the brief conflates them; `ogs_at_or_above_40 = 251` is an upper bound for the ≥ 41 rule). Rejected anyway: nothing in the issue or the data derives "two", so it is a preference dressed as a threshold.

**Conditions.** The refusal uses house vocabulary and refuses honestly — never a zero, never a stale number (ADR 0120, the `SetTooLarge` precedent). Each resolved group carries its own state, so a mixed result (some groups above 21, some below) renders per group rather than refusing wholesale. **Named consequence for Klas: 21.5 % of occupation groups will show a refusal rather than a map.**

## D5 — copy form for share + count

**Verdict: the share is the claim, the count is its evidence, and the window is disclosed once at block level. Form: `48 % (412 annonser)`. The middle dot is unavailable.**

**Binding reason.** My 2026-09-14 ruling on #1715/#1711 bound the middle dot as the **axis separator** across three delivered docblocks and rejected variant C precisely for *"reus[ing] that glyph to join two levels on one axis."* Share and count are two readings of one axis — the same quantity at two scales — so `86 Hälso- och sjukvård · 48 % · 412 annonser` and `48 % · 412 annonser` are both out, by the ruling that is two clicks away on the same screen. The parenthesis subordinates evidence to claim, which is what AGENTS.md §5 asks of a derived number (*"matched/missing keywords are always surfaced — explainable by design"*): the count is what stops the share being opaque.

**The real hazard the brief does not name: `annonser` would mean two populations.** On `/foretag/branschbevakningar` two clicks away, `annonser` means live ads; here, under Klas decision 2, it means every ad we have ever seen. That is exactly the collision my #1711 ruling closed with *"Nothing means two things anywhere"* (Evans 2003, ubiquitous language).

**Resolution — one home, block level.** The block's intro sentence states the basis and carries the group total N (which is also what the D4 floor keys on); the rows then carry bare `48 % (412 annonser)`. DRY in its real sense: one knowledge piece, one home, not one sentence per row. The `ej i registret` bucket takes the same form as a plain line, not a checkable row (issue scope 1 + 2).

**Ruled out.** `412 annonser, 48 %` — it leads with the evidence and buries the ranking quantity the user is scanning. Any per-row noun long enough to disambiguate the window — it pays the disclosure on every row for a fact that is true of the whole block.

**Needs Klas (product vocabulary, not mine):** the exact Swedish noun and the intro sentence's wording, with `design-reviewer` ruling the form. `aktiva annonser` is forbidden by his own decision 2.

## D6 — Deregistered register rows

**Verdict: include — written as a POSITIVE allow-list, `status = ANY('{Active,Deregistered}')`. Never `status <> 'Deregistered'`, never no predicate.**

**Binding reason — purpose, not parity.** ADR 0139 Major 3 removes `Deregistered` from **watch membership** because a watch is forward-looking and a dead company in a live watch is an Art. 5(1)(d) accuracy defect (DPIA M-D6/R-D6). This profile is **backward-looking and aggregate**: it carries no company identity, is not person-attributable, and answers *where did employers who advertised for this occupation sit*. A company that has since been deregistered **was** part of that population; dropping it removes evidence from a count, which inverts the explainability doctrine the count exists to serve. Different purpose, different rule — parity is not owed. (27 of 80 243 = 0.03 %, so this cannot be decided on impact; it is decided on meaning.)

**Why the form matters more than the answer.** `CompanyWatchBrowseQuery.FromWhere` states the house rule verbatim: *"`status = @status` is deliberately POSITIVE polarity … the day `CompanyRegisterStatus` gains a third member, the negative form starts silently SURFACING it … the #805-3 failure shape."* `CompanyRegisterStatus` is documented as *"deliberately two-valued"* with richer states explicitly projectable later. So a negative predicate — or none at all — would silently admit a future third member (a GDPR-erasure state, say) into a published aggregate. The allow-list is the same shape the `job_ads` side already takes (#864 D4): **allow-lists on both sides of the join, stated, never inherited.**

## D7 — SNI code in the filter rows

**Verdict: the accessible name KEEPS the code, unchanged. The visible form is `design-reviewer`'s.**

**Binding reason — two independent WCAG obligations, and only one is design's.**

- **WCAG 1.3.1.** `criterion-picker.tsx:317-321` documents the measurement: *"In a filtered list the ancestors are not rendered, so equal indent on two rows can suggest a sibling relationship that does not exist — and padding reaches no screen reader at all … The CODE carries the level in text: its length says which level it is (`A` / `62` / `62100`) … SNI 2025 has 'Dataprogrammering' at two levels; its codes differ."* Rows are `role="checkbox"` (not `treeitem`), so `aria-level` is not valid on them — the code in the name is the **only** available carrier. Strip it from both the row and the name and the hierarchy becomes presentational only: a 1.3.1 regression, and design-reviewer's veto does not extend to creating one.
- **WCAG 2.5.3** is a **one-way** constraint: the accessible name must *contain* the visible text, not equal it. Hiding the code visually leaves `"Fastighetsverksamhet"` ⊂ `"68 Fastighetsverksamhet"`. It holds.

**Rules out.** `aria-describedby` + visually-hidden span — cleaner on paper, but descriptions are verbosity-gated and suppressed outright in some AT modes; a load-bearing relationship must not live where announcement is optional. **Hover/focus as the accessibility carrier** (issue scope 4's secondary suggestion) — hover reaches neither keyboard nor touch, and focus reaches no browse-mode reader. As a *visual* affordance it is design's call; as the a11y carrier it is refused here.

**Conditions.**
1. The `aria-label` expression at `:302-306` is **unchanged**. The delivered coupling comment says *"anything visible added to this row has to be added here too"*; that governs additions, and a removal cannot break 2.5.3.
2. **The comment's factual claim becomes false and must be fixed in the same PR.** *"The visible text is exactly this string"* stops being true the moment the code is hidden — AGENTS.md §5: *"A factually wrong comment … is a defect and is fixed."* Rewrite it to state the superset and why (1.3.1 carrier), not to narrate the change.
3. **Named accepted trade-off:** speech-input users now say a string that is a substring of the name rather than the whole name (WCAG 2.5.3 Understanding recommends, but does not require, the visible label leading the name). Small, real, and worth stating rather than discovering.
4. The new occupation block's rows are picker rows and inherit rule 1 verbatim.
