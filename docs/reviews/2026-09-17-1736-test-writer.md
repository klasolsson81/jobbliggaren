`tests/Jobbliggaren.Worker.IntegrationTests/Migrations/AddTermsAcceptanceToJobSeekerMigrationTests.cs:96-138`, comment at `:123-125`.

The comment nonetheless writes the effect as fact: *"the columns were added to a table that already had rows, so a NOT NULL here would have failed the deploy against a populated database."* That is an argument standing in for a measurement.

The uncovered mutant is specific and consequential: adding `defaultValue: "2026-09-17"` (or `defaultValueSql`) to any of the three `AddColumn` calls keeps `is_nullable = YES`, passes this test, **and** passes all three `TermsAcceptanceBackcompatTests` — which seed *after* the migration through `JobSeeker.Register` (`:53-55`) and then NULL the columns by raw SQL (`:68-72`), so a column default never applies to their rows. (Exposure today is two rows, both Klas's, per the not-launched posture; the guard is what I am grading, not the exposure.)

*Fix, in-block and in `tests/**`:* the journey already visits `PreviousMigration` at step 2. Between step 2 and step 3, `INSERT` one raw `job_seekers` row (the NOT NULL set at that migration is roughly `id, user_id, display_name, created_at, match_preferences, preferences` — read it from the schema at `PreviousMigration` rather than from the current snapshot), then migrate forward and `SELECT terms_accepted_at, terms_version, privacy_policy_version` for that id and assert all three `IS NULL`.
