### 1. Q1: the outcomes after proof, and the line between 1a and 1c

**Decision:** option (c). I reject both (a) and (b) as they were posed.

- **The mail is chosen at issue time, and D2 governs it.** `RegistrationClosed` and `PendingDeletion` mails carry no code and no link.
- **The outcome is chosen at proof time.** One function serves both verify and link. It resolves the subject at that moment (R6/R13):

  | Subject at proof time | Outcome |
  |---|---|
  | `Active` | `signedIn`, with a session |
  | `PendingDeletion` | `pendingDeletion` (with the date), no session |
  | `NoAccount` or `ProfileMissing` | `registrationClosed`, no session |

  **1a ships this whole function.**
- **1a never mints a code for a subject without an account.** Its plan sends `NoAccount`/`ProfileMissing` to `RegistrationClosed` whatever `RegistrationsOpen` says.
- **1c adds the open-registration arm in one piece:** `NewAccountCode`, `NewAccountCodeLimitReached`, `consentRequired` + grant, and `complete`.

**Principles:**
- **CCP/SRP at the PR level** (Martin 2017, ch. 7, 13). The new-address mail, its budget-exhausted mail, the grant and `complete` all change for one reason: passwordless registration. If the mail ships in 1a and the capability in 1c, 1a sends a mail that says *"Du skapar ett nytt konto"* with a code that can only lead to a refusal.
- **Expand-only** (Fowler 2018, *Parallel Change*). Every arm 1a writes is permanent, and 1c only adds. Nothing gets written just to be thrown away.
- **Reading the kill-switch at proof time** is the only way to honour a `RegistrationsOpen` switch thrown inside the 15-minute window (R6).
- **The ADR contradiction goes away.**
  - D2:150-151 decides what the mail says, and the mail is the authority (Page form :604-609).
  - D3:174-175 and Page-form states v/vi stay reachable when the state changes between mint and proof, which is exactly when a page state is needed.
- **`ProfileMissing` is grouped with `NoAccount`** because the domain already treats it that way: the sweep deletes an Identity row with no `JobSeeker` after one hour (`AccountHardDeleter.cs:40-53`). The #1349 guard holds by type, because the grant takes only `LoginSubject.Active` (`LoginCommandHandler.cs:60-71` is the capability seam).

**Rejected:**
- **(a)** ships `consentRequired` without the `grantToken` that makes it usable. That is a wire contract for a capability that does not exist, and 1c would then change its shape.
- **(b)** ships an interim refusal that 1c deletes, next to a `NewAccountCode` mail that promises account creation. That is throwaway code plus a false mail.
- **Pulling the grant port into 1a** would ship `RedeemAsync` with no caller (the architect's own argument against `TryClaimAsync`, R5).

**Trade-off:** until 1c lands, a host with `RegistrationsOpen=true` (`ApiFactory.cs:209`) sends the closed mail to a new address. No real person can receive it:
- The box measured `RegistrationsOpen=false` on 2026-09-18.
- `ConsoleEmailSender` writes no body for a non-reserved recipient.

### 2. Q2: "missing is shown as expired"

**Decision:** option (a).
- Delete D3's clause *"(the holder's challenge existed; only expiry removes it)"* and replace it with the list of causes.
- Delete Page-form state iv (:621).
- Delete the first sentence of the resting hint (:606-607): *"Har du redan begärt en kod nyss kan det vara den som gäller."*
- Record security's two Minors in the amendment as accepted residuals: the address-activity signal and the link-use existence signal.

**Principles:**
- **The hint is false in every case it was written for.**
  - A cooled re-request gives the cookie an id with no record behind it, so the earlier code cannot be verified from that cookie.
  - An admitted re-request writes a code-bearing record, and that `Put` deletes the earlier record (R8).

  The fix is to delete the sentence (§9.6: "a fix deletes text"). The second sentence stays true.
- **YAGNI and Art. 5(1)(c)/(e).** Option (b) keeps a payload that holds a credential after its purpose has ended.

**Rejected:**
- **(b)** Security grades the ungated form a Major. The gated form still cannot fix the cooled case, because no record ever existed there.
- **(c)** It removes the cooldown that both the reorder and the protection against immediate replacement depend on (security Q2(c)).

**Left open for part 2:** keeping the live cookie when the same address is re-submitted inside the cooldown window is allowed, but not required. That is FE's and design's call.

### 3. Q3: constants or options

**Decision:** the planner's proposal, which security has accepted.
- **Constants in one Application `LoginChallengePolicy`:** code length 6, attempts 3, TTL 15 min, `MailBudget` 3/10 min, `CodeBudget` 10/24 h.
- **`[Range]` options with code defaults:**
  - Capacity: `LoginChallengeDispatchOptions.Capacity`.
  - Cooldown window: `AuthEmailCooldownOptions.LoginChallengeWindowSeconds`, `[Range(1,3600)]`, default 60, following the precedent at `AuthEmailCooldownOptions.cs:46-47`.
- **§11 is not triggered.** Neither option is a required key. D10:469-470 is corrected rather than followed.

**Principle:** Twelve-Factor III. Config is what varies between deploys, and the parameters of a measured acceptance with lapse triggers must not vary. If they could change through an env var, trigger 5 would fire with no PR, no panel and no measurement. The budget is policy, and policy belongs in code (Martin 2017, ch. 19).

**Rejected:** all parameters as options. That lets config move a security acceptance silently.

### 7. F3: a new address whose code budget is spent

**Decision:** the variant `NewAccountCodeLimitReached` exists, and it **lands in 1c** with the rest of the open-registration arm (section 1).

**Principles:**
- **SRP of the two scopes.** `MailBudget` caps mails for every address, and `CodeBudget` caps codes. Without the variant, `CodeBudget` would also cap mails in exactly one cell of the table, which couples the two.
- **The plan stays total**, with exactly one mail per cell.
- **D2's "one mail" premise stays true.** Trigger 7 and the resting copy rest on it.

**Rejected alternatives:**
- **No mail:** the resting copy becomes false and trigger 7 fires.
- **The closed mail:** its content is false.
- **A code:** that breaks the guess budget.

**Trade-off:** the per-address ceiling for a new address rises from 10 mails a day to 18 an hour when registration is open. That equals the ceiling that already applies to closed-registration and `LinkOnly` mails. Security grades the copy and recipient class (3) in 1c.

## Consolidated binding list

**PR structure**
1. Two PRs under #1735: first the prep PR, then the feature PR (section 9).

**Request path**
2. **`POST /auth/challenge` order:** validate → `CanDeliver` → mint `ChallengeId` → cooldown scope → `MailBudget` → `CodeBudget` (a classifier, never a refusal) → `Enqueue` → 202 `{challengeId}` on every exit except 503.
   - It reads no account (A1 as amended).
   - Each gate runs only if the one before admitted the request (security Q18.1).
   - A request refused by the cooldown or `MailBudget` is silent: no enqueue, no record.
3. **`IRateBudget`:**

   - Atomic form: `MULTI{INCR; EXPIRE … NX}`; admitted if and only if `count ≤ Limit`. No key ever exists without a TTL (R4; security).

      - `a` = the attempt counter.
    - No stored subject flags and no `expiresAt` (R6).

    - `MULTI{HSET p a=0; PEXPIRE; [code minted] SET index … PX … GET}`, then `DEL` of the displaced predecessor.

13. **Code consume:**

14. **Burn affects the code arm only.** A record leaves Redis only through:
    - a successful consume on either arm (`DEL`=1),
    - a newer code-bearing Put, or
    - its TTL.

    A fourth verify answers `Burned` (R1/R7). Pending Q-S1.
15. **Link consume:**

    - `DEL`=1 yields the proof. This path never reads or writes `a` (R9).
